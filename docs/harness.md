# Харнес v0

Реализация: `runtime/harness.py`, функция `run`. Для небольших правок system prompt рекомендует точечную замену байтов через Python,
чтобы сохранить форматирование и завершающий перевод строки. Никакого планировщика,
RAG, суммаризации памяти и субагентов. Модель предлагает действия, цикл выполняет
их по очереди и возвращает результаты модели.

| Механизм | Где и как |
|---|---|
| Контекст | `context`: system + последние MEMORY_TURNS полных ходов + user |
| Агентный цикл | `run`: `complete(messages)` → tool calls → исполнение → следующий запрос |
| Остановка | Ответ без tool calls, cancel, MAX_STEPS (8), проверка бюджета 180 секунд |
| Диспетчеризация | В `run` разрешены только ReadFile, WriteFile, RunCommand |
| Ошибки тулов | Невалидный вызов → tool_error; ошибки sandbox возвращаются модели как JSON |
| Исполнение | Callback из `Gateway.worker` вызывает HTTP `/v0/exec`; subprocess только в sandbox |
| LLM-прокси | `runtime/llm.py:complete`, backend mock/openrouter из окружения |
| Трейс | `Gateway.emit`: JSONL с trace/session id, run id, seq, временем, usage и исходами |

Ход хранится целиком: нельзя отрезать tool result от assistant tool call.
Незавершённые/отменённые ходы не сохраняются. MEMORY_TURNS=0 выключает историю.
Текущий ход не обрезается; его объём ограничивают 8 итераций, до 8 вызовов за ответ,
32 KiB вывода каждого инструмента и 2048 выходных токенов модели.
Обрезанный вывод помечается `truncated=true`.

Бюджет 180 секунд кооперативный, проверяется между вызовами. Один HTTP-вызов LLM
имеет socket timeout 60 секунд, команда — 10 секунд по умолчанию, максимум 30.
Это не строгий wall-clock deadline против сервера, который присылает ответ по байту.
Cancel немедленно посылается sandbox, но финал при ожидающем LLM может задержаться
до возврата/таймаута HTTP-запроса. Строгие deadlines и отмена HTTP — дальнейшая работа.

Менять пару можно без правки кода: `LLM_MODEL`, `MEMORY_TURNS`, `MAX_STEPS`.
Для эксперимента возможны варианты одного харнеса: память 0 и 2 хода.
Сравнение разных реализаций харнеса пока не реализовано. Выбор модели не сделан.

Sandbox v0 — один заранее поднятый compose-контейнер. Объём /work 32 MiB,
/tmp 16 MiB; CPU 0.5, RAM 128 MiB, PIDs 32, uid 10001, read-only root,
cap-drop ALL, no-new-privileges. **Наличие настроек не заменяет тесты лимитов.**
Файловые тулы проверяют relative path, выход через symlink, `.git` и `.runtime`.
RunCommand может обойти файловые запреты внутри контейнера, использовать /proc
и создавать новую process session. Это не окончательный security boundary:
тест cancel проверяет обычное дерево в process group, не злонамеренный `setsid`.
Перед ЧП2 нужны разделение supervisor и команды, защита служебных путей на уровне
mount/прав и уничтожение всего sandbox при завершении сессии.
